One FMI LS WASM FMU can, in principle, execute internally on multiple cores. Packaging one graph does not require single-core execution. Rumoca's current implementation does not automatically parallelize that graph.

Read-only review, 2026-10-05; no compiler changes, builds, worker prototype, or threaded runtime acceptance.

The distinctions matter:

- [FMI 3.0.2 §5](https://fmi-standard.org/docs/3.0.2/#scheduled-execution) explicitly permits internal multicore computation, outside the standard's control. Its Scheduled Execution interface defines priorities, partition activation and preemption on a computational resource. The same section explicitly excludes parallel computation of model partitions from the FMI API. SE therefore is not a standard guarantee that an importer may simultaneously execute arbitrary partitions of one instance.
- [FMI 3.0.2 §2.2.1](https://fmi-standard.org/docs/3.0.2/#requirements-for-implementations-of-the-c-api) does not require same-instance FMI functions to be thread-safe. An importer must prevent races when it invokes them from multiple threads. Logger and preemption lock/unlock callbacks cannot call back into the FMU; intermediate-update and clock callbacks have specifically defined legal states. A package or WIT resource does not supply missing synchronization or permit unrestricted reentrancy.
- The current [WASI SDK](https://github.com/WebAssembly/wasi-sdk#notable-limitations) lists experimental thread spawning under `wasm32-wasip1-threads`; `wasm32-wasip2` is its Component Model target. Thread APIs being present in headers is not proof that spawning works for that target. The official [legacy wasi-threads proposal](https://github.com/WebAssembly/wasi-threads) routes future component threading toward shared-everything threads. The [FMI LS WASM draft](https://github.com/modelica/fmi-ls-wasm#known-limitations-and-future-work) itself flags evolving component threading support. Do not equate async component calls or a worker hosting a component with parallel execution of its kernel.
- Core browser WASM can use workers, shared linear memory and atomics. The [WebAssembly threads design](https://github.com/WebAssembly/threads/blob/main/proposals/threads/Overview.md#shared-linear-memory) requires a matching shared-memory import; replacing an unshared import's buffer is invalid. Shared browser buffers require a secure, cross-origin-isolated context; typical deployment uses COOP `same-origin` and COEP `require-corp` or `credentialless`. [MDN isolation requirements](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer#security_requirements), [COOP configuration](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Opener-Policy#features_that_depend_on_cross-origin_isolation). Adapter/runtime/thread-host support still has to be qualified for the particular component.

A viable later design keeps one public FMU lifecycle and one committed instance state, while the compiler schedules certified independent pure kernels internally. Workers share immutable input/parameter snapshots, write disjoint candidate outputs and own separate scratch/frames; dependency barriers precede consumers and a single checked publication point commits results. Preserve original operation arithmetic, sequential fold/reduction/RNG/effect order, call-owner provenance and deterministic first-fault selection. Current target certificates must be extended with genuine concurrency proofs; disjoint output ranges alone do not establish independence. A worker failure must not expose partial estimator/reference state. This uses local shared memory and barriers, not distributed nodes or per-edge FMU-state serialization.

That is a future compiler/deployment capability, not a prerequisite for finishing current full-source Modelica SLAM. First obtain the executing, numerically qualified graph. Then qualify a threaded profile against the same serial source-issued artifact and failure semantics.
