FMI LS WASM is a sensible eventual deployment form for one compiled Modelica SLAM graph. It is not currently a shortcut around full-frame Solve/native admission. Keep the immediate full-source native work; unify deployment through checked Rumoca kernel/export owners once that graph executes.

This is a read-only source and primary-specification review on 2026-10-05. No compiler edits, compilation, FMU export, browser component execution, or full SLAM acceptance was performed.

The upstream [FMI LS WASM repository](https://github.com/modelica/fmi-ls-wasm) explicitly describes an actively changing, non-normative prototype mapping of FMI 3 to WIT. Rumoca pins revision `c1aac17d392bec989fe2d059db3cc57bb7a0fff5`; adoption claims must remain tied to that draft. Its WIT includes typed arrays and serialized state; the presence of a method in WIT does not establish exporter support.

The LS target emits a component crate, not itself a complete FMU archive: its manifest declares no `modelDescription.xml`; the existing component test obtains value references by separately rendering the `fmi3` model description (`crates/rumoca/tests/suite_template_runtime/fmi_ls_wasm_runtime.rs:108`). An eventual archive must bind matching metadata, component, capabilities, resources and identities from one checked export aggregate. Accepted `spec/SPEC_0007_IR_PIPELINE.md:63` requires precisely that ownership; `SPEC_0038_UNIFIED_FMI_EXECUTION.md` is currently DRAFT, so its intended unification is not evidence of implemented support.

Browser transport adds work. Official [Component Model JavaScript guidance](https://component-model.bytecodealliance.org/language-support/building-a-simple-component/javascript.html#running-a-component-from-javascript-applications-including-the-browser) currently uses `jco transpile` to produce JS adapters and core modules for browsers. This generated interface glue is compatible with keeping all model mathematics in Rumoca. The [Canonical ABI](https://github.com/WebAssembly/component-model/blob/main/design/mvp/CanonicalABI.md#storing) allocates/stores list elements; implementations can optimize transfers, but WIT lists do not promise shared-memory or zero-copy access. Batch whole arrays and small output groups; do not cross WIT per pixel. One 160×90 RGBA input is 57,600 bytes as U8, 230,400 as F32, 460,800 as F64; depth is 57,600 as F32 or 115,200 as F64. These are exact payload sizes, not measured overhead. Current LS accessors cannot preserve U8/F32 transport directly. FMI accessors must match declared FMI variable types; enabling methods alone cannot make a Float64 Real array a UInt8 array.

The upstream WIT maps `get-fmu-state` directly to serialized bytes. Large snapshots can therefore copy images, descriptors and estimator state; save checkpoints when needed rather than round-trip serialized state every frame. Current stateless localization source explicitly carries state through inputs/outputs; packaging it does not create persistent Modelica state. Moving those updates inside the model later requires checked discrete/clock lifecycle admission.

[FMI 3.0.2](https://fmi-standard.org/docs/3.0.2/) distinguishes CS-owned stepping, importer-owned ME integration, and importer-activated SE partitions. For the present lockstep capture, CS communication boundaries are practical: await the GPU batch, set frame inputs, advance exactly the intended interval, then read accepted outputs. ME fits externally controlled integration; SE fits separately scheduled IMU/image partitions if the compiler and export genuinely support their clocks. FMI 3 removed its asynchronous CS mode, so none of these eliminates GPU waiting. Existing `src/gpu-readback.ts:107` already submits one capture batch, fences, polls asynchronously, then copies through `getBufferSubData`; preserve timestamp/epoch ownership and prohibit silently using a stale frame while waiting.

The current carried-state localization step contains no `der`, `when`, `pre`, or Modelica Clock operator; host image epochs are ordinary inputs. Existing `models/ModelicaInertial.mo` does contain continuous derivatives. Neither source shape is proof of clocked SE admission. Package the numerical graph while leaving WebGL rendering/capture in its host; this FMI component has no implemented GPU resource bridge.

Recommended sequence: finish actual original full-frame and connected localization native admission first; preserve source edits, guarded borders, covariance coupling, faults and commits. Then admit that same checked source graph in the FMI export profile, filling only demonstrated generic operation/type/lifecycle gaps. Package one graph with matching XML and immutable provenance, prove native-versus-FMU numerical and failure parity, then qualify the browser adapter with real full images. Add internal persistent/clocked state only when lifecycle tests establish it. This delivers a reusable graph package without an app compiler or parallel model semantics.

Current scope remains localization, not completed loop-closing SLAM: `models/RGBDInertialSLAM.mo` is explicitly partial. Reviewed stable localization sources have no newly found causal cycle or optical sign mismatch; all reference snapshots commit iff captureAccepted. Their actual native admission is still a separate gate. Do not label either source existence or a successful small FMU example as full SLAM acceptance.
